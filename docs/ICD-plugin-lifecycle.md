## Purpose

The plugin subsystem is the in-browser extension point: third-party JavaScript that runs **in-process with full `window` + `AIEditor` access** and contributes hooks, toolbar buttons, modals, tools, CSS, and MCP server registrations. It exists alongside a separate Tier-0 LLM-authored automation sandbox ([`DESIGN-llm-authored-automation.md`](DESIGN-llm-authored-automation.md) — Worker-based, untrusted-by-default, approval-gated) — the two **share no code path**. Plugins are trusted-by-install; the only pre-execution gate is the invisible-Unicode scanner ([`js/security/invisible-unicode.js`](../js/security/invisible-unicode.js), reused from the 2.17.1 tool-return scan). The Worker sandbox is the LLM's tier-0 path; plugins are the human-author's first-class extension surface.

Three persistence stores hold plugin state, all in `localStorage` via `Storage`:

- **`installedPlugins`** — `InstalledPlugin[]` for URL-installed externals. Owned by [`plugin-loader.js`](../js/plugin-loader.js); written on install, mutated on boot-load error, deleted on uninstall.
- **`userPlugins`** — `{[id]: {source, name, savedAt}}` for in-editor-authored plugins. Owned by [`plugin-editor.js`](../js/plugin-editor.js); written on save / hot-reload, deleted on Delete-from-tab.
- **`pluginState`** — `{[id]: {enabled, config}}` for runtime state across **all** plugins (bundled / external / user). Owned by `Plugins._persistState` in [`core.js`](../js/core.js); written on every `setEnabled` / `setConfig` flip.

Bundled plugins ship under `js/plugins/*.js` and load via static imports in [`js/app.js`](../js/app.js); they have no `installedPlugins` or `userPlugins` record. The post-2.54.0 admission inversion ([github#40 paper-cut](https://github.com/gobha-me/ai-editor/issues/40), closed 2026-05-15) means plugin-side registration is admission-tag-free — tools register without `roles:` tags, and admission flows through profile-side `tools.admit` arrays + the `plugin.enabled` overlay. The `plugin-dev.v1` synthetic profile + the 2.58.0 capability overlay are the two paths a user reaches the 5-tool plugin-dev cohort. **This ICD freezes the per-plugin lifecycle (install → register → enable → invoke → cleanup), the three persistence stores' schemas, the auto-profile-switch UX contract on the plugin-editor tab, and the no-sandbox property so the next contributor reading the code sees what's load-bearing vs. incidental.**

## The five classification axes

Each axis names a question the seam answers across the in-process registry + the two persistence stores + the three load paths (bundled / external / user). The first three (Installation, Registration, Enablement) describe *how a plugin enters the running system*; the last two (Invocation, Cleanup) describe *what happens once it's there and when it leaves*.

| Axis | Question | Where it's declared | Where it's read |
|---|---|---|---|
| **Installation axis** | How does a plugin enter the system, and what is the per-source acceptance gate? | Three sources, three entry shapes: **bundled** plugins are static imports in [`js/app.js`](../js/app.js) — no installer call, no persistence record, code path is just a module-level `Plugins.register(manifest)` at import time; **external** plugins flow through `installPlugin(url, opts?)` ([`plugin-loader.js:61`](../js/plugin-loader.js)) — fetch source → invisible-Unicode scan → blob-URL `import()` → snapshot-diff detection of newly registered IDs → `Plugins.init(id)` → append `InstalledPlugin` record to `installedPlugins`; **user-authored** plugins flow through `_save(id, source, name)` ([`plugin-editor.js:31`](../js/plugin-editor.js)) → `userPlugins[id]` blob → reload-time `loadUserPlugins()` does the same blob-URL `import` cycle. **Invisible-Unicode scan is the sole pre-execution gate** — `installPlugin` returns `{requiresConfirmation: true, invisibleUnicodeFindings: [...]}` on detection ([`plugin-loader.js:90–100`](../js/plugin-loader.js)); Settings UI surfaces a band with per-finding line/col/codepoint and an "Install anyway" affordance ([`plugins-tab.js:395`](../js/settings/plugins-tab.js)); user can bypass via `{confirmedInvisibleUnicode: true}` re-invocation. **User plugins skip the scan entirely** — the assumption is the author wrote the code themselves; finding #3 below queues a question about persisting bypass decisions on installed externals. | `loadInstalledPlugins()` ([`plugin-loader.js:186`](../js/plugin-loader.js)) re-runs `fetch` + blob-import + `init` for every persisted external on boot; `loadUserPlugins()` ([`plugin-editor.js:395`](../js/plugin-editor.js)) does the same for every persisted user plugin. Admission of those 5 tools flows through profile `tools.admit` enumeration (in `plugin-dev.v1`) **or** the `plugin.enabled` capability overlay (gated at [`applyPluginToolFilter`](../js/llm/api.js)) — the dual path lets users keep their active profile + flip plugin-dev tools on, rather than burning the profile state on a switch. |

Five axes × three load paths (bundled / external / user) × three persistence stores (`installedPlugins` / `userPlugins` / `pluginState`) × three invocation surfaces (hooks / tools / UI) is the surface this ICD pins.

## Per-axis contract

### Installation axis — pre-execution gate + persistence record invariants

The installer enforces five invariants:

1. **Duplicate-URL rejection.** `installPlugin(url)` short-circuits if any `installedPlugins[*].url === url` ([`plugin-loader.js:69`](../js/plugin-loader.js)) — protects against double-install if the user pastes the same URL twice. URL is trim()ed before comparison; query strings count toward identity (same path with different `?v=` counts as a different plugin).
2. **AIEditor signature check.** Fetched source must contain `'Plugins'` or `'AIEditor'` substring ([`plugin-loader.js:85`](../js/plugin-loader.js)) before execution — a syntactic smoke test that the file is plausibly an AI Editor plugin, not random JavaScript. This is a heuristic, not a guarantee.
3. **Invisible-Unicode pre-flight scan.** Calls [`security/invisible-unicode.js`](../js/security/invisible-unicode.js)'s `scan(source)` ([`plugin-loader.js:91`](../js/plugin-loader.js)); on non-empty findings, returns `{success: false, requiresConfirmation: true, invisibleUnicodeFindings: [...]}` **without executing the source**. Caller re-invokes with `{confirmedInvisibleUnicode: true}` to bypass — the bypass decision is **not persisted** to the `InstalledPlugin` record (this is finding #3).
4. **Blob-URL import isolation.** Source loads via `URL.createObjectURL(new Blob([source], {type: 'application/javascript'}))` + dynamic `import()` ([`plugin-loader.js:104–111`](../js/plugin-loader.js)) — bypasses CORS issues that `import(url)` directly would hit on cross-origin sources. Blob URL is revoked in the `finally` block. This is **not a sandbox** — the imported module executes with full `window` + `AIEditor` access; blob-URL isolation only prevents one specific class of cross-origin breakage.
5. **Registration-snapshot diff.** Pre-import, the installer snapshots `Plugins.list().map(p => p.id)` ([`plugin-loader.js:74`](../js/plugin-loader.js)); post-import, it computes the set difference to find the newly registered ID. If no new ID appears, throws `'Plugin loaded but did not call Plugins.register()'` ([`plugin-loader.js:118`](../js/plugin-loader.js)). This is the only validation that the source actually contributed a plugin — there's no manifest-shape check beyond what `Plugins.register` itself does (`id` + `name` required).

`InstalledPlugin` record schema (`installedPlugins[]`):

```
{
  url: string,                  // source URL (identity key)
  pluginId: string,             // newly registered id from snapshot diff
  name: string,                 // manifest.name at install time
  installedAt: string,          // ISO timestamp
  error: string | null          // last load error from loadInstalledPlugins re-fetch; null on success
}
```

**Five fields, no schema versioning.** The `error` field is the only mutable post-install field — every `loadInstalledPlugins()` re-fetch clears or sets it ([`plugin-loader.js:221, 226`](../js/plugin-loader.js)). Finding #3 proposes adding `invisibleUnicodeWarnings?: Array` to surface the bypass decision in audit; the field would be opt-in (absent on plugins installed before the field shipped) so back-compat is automatic.

User-plugin record schema (`userPlugins[id]`):

```
{
  source: string,               // full plugin JS source
  name: string,                 // extracted from `name: '...'` regex at save time
  savedAt: string,              // ISO timestamp of last save
}
```

**Three fields, no schema versioning.** No `error` field — failures surface in the editor's status bar ([`plugin-editor.js:344`](../js/plugin-editor.js)) but aren't persisted because the user is right there to react. No `pluginId` field — derived at runtime from the snapshot-diff load, same as externals; the storage key **is** the id.

Runtime state schema (`pluginState[id]`):

```
{
  enabled: boolean,             // last-flipped state, sticky across reloads
  config: Object,               // plugin's config bag, shape per manifest.configSchema
}
```

**Two fields.** Source-of-truth for the `enabled` flag is the in-memory `_registered[id].enabled` cell; `pluginState` is the persistence shadow. `config` is opaque to the registry — `manifest.configSchema` declares per-field shape for the Settings UI to render input controls, but the registry just round-trips the object.

### Registration axis — manifest contract + de-dup invariants

`Plugins.register(manifest)` enforces six invariants:

1. **Required fields are `id` + `name`.** Both must be non-empty strings; otherwise `console.error('Plugin missing id or name')` + return `false` ([`core.js:1071–1074`](../js/core.js)). No length / character-class / prefix validation; `id` is opaque downstream — the Settings UI uses it as a DOM data-attribute, the storage layer uses it as an object key, and the Plugins namespace uses it as a Map key. The only practical constraint is "must be valid as a localStorage object key + an HTML data attribute value" — i.e. no `'`/`"` in the id.
2. **Last-wins on duplicate registration.** A second `register(manifest)` with the same `id` overwrites `_registered[id]` in place — buttons / modals / hooks / tools registered by the first call **survive** (they're in `_buttons` / `_modals` / `_hooks` / `ToolRegistry` separately), so the second call's `init()` running adds rather than replacing. This is the hot-reload property the plugin editor's Run button depends on: re-importing the same source re-registers the plugin with the same id, and `Plugins.init(id)` is called after to refresh the live instance. **No HMR-style teardown is performed** — the previous instance's `init()` return value is replaced in `_registered[id].instance`, but its side effects persist. See finding #2 for the related auto-profile-switch concern; the manifest re-registration property is a different antibody (intentional, for the Run-button workflow).
3. **`enabled` flag resolution order.** On register: read `Storage.get('pluginState')[id].enabled` if present; else `manifest.defaultEnabled` if defined; else `true` ([`core.js:1082`](../js/core.js)). The Settings UI's toggle flips through `setEnabled` (not direct mutation), preserving the lazy-init antibody.
4. **`hooks` array declares — function lives on manifest.** `manifest.hooks: string[]` is a declarative list; for each entry, `runHook(name, data)` reads `manifest[name]` and calls it. **Declaring without defining is silent**: a `hooks: ['beforeSend']` without a `manifest.beforeSend` function just no-ops at fan-out (the `hookFn` check at [`core.js:1153`](../js/core.js) skips). Declaring-the-name-twice-in-different-plugins is fine — each plugin's id lands in `_hooks[hookName]` once.
5. **`defaultConfig` is shallow-cloned on first-register only.** When `pluginState[id].config` is absent, the registry seeds `config: {...manifest.defaultConfig}` ([`core.js:1084`](../js/core.js)) — a shallow clone, not a deep one. Plugins with nested default config (e.g. `{nested: {key: 'val'}}`) will share the inner object across `getConfig` calls until `setConfig` writes a fresh top-level object.
6. **`plugin:registered` EventBus emit is unconditional.** Even on hot-reload re-register, the event fires ([`core.js:1098`](../js/core.js)) — downstream consumers (Settings tab refresh listener) handle de-dup themselves. No `plugin:reRegistered` or `plugin:updated` distinct event today; consumers that need to distinguish first-register from re-register must track state themselves.

### Enablement axis — first-enable init antibody + capability overlay

The `setEnabled` contract carries the load-bearing antibody at [`core.js:1227`](../js/core.js):

```
if (enabled && !wasEnabled && !plugin.instance && plugin.manifest && plugin.manifest.init) {
    plugin.instance = await plugin.manifest.init(plugin.config);
    EventBus.emit('plugin:initialized', pluginId);
}
```

Five invariants on `setEnabled(id, bool)`:

1. **Flag flip is synchronous; init is asynchronous.** Callers that don't `await` see the boolean update immediately + the EventBus `plugin:enabledChanged` event fire; the optional `init()` runs after the function returns. The Settings tab UI's toggle handler doesn't `await` ([`plugins-tab.js:296`](../js/settings/plugins-tab.js)) — the re-render after `populatePluginsTab()` re-reads the synchronous flag.
2. **First-enable init runs only once per session.** Guards: `!wasEnabled` (was disabled) + `!plugin.instance` (no prior init) + `manifest.init` exists. Re-enabling a plugin that already has `instance` (was enabled earlier in the session, disabled, re-enabled) skips init — by design, since `instance` already set up buttons / modals / hooks / tools at first-enable.
3. **No symmetric `destroy()` call on disable.** This is finding #1. The Cleanup axis describes the reload-to-fully-remove property; the absence here is what makes that property load-bearing.
4. **EventBus emit fires before init.** `plugin:enabledChanged` ([`core.js:1221`](../js/core.js)) emits with the new flag value before the lazy init runs. Listeners that depend on the plugin's instance / registered tools must subscribe to `plugin:initialized` ([`core.js:1230`](../js/core.js)) instead — fires only on first-enable + after init completes.
5. **Init errors don't unflip the flag.** If `manifest.init(config)` throws, the catch at [`core.js:1232`](../js/core.js) logs but **leaves `plugin.enabled === true`** — Settings UI shows the plugin as enabled even though its init failed. The error surfaces only through the `console.error` line + (for boot-time inits) the `plugin:initError` EventBus event ([`core.js:1125`](../js/core.js)). The `setEnabled` first-enable branch does not emit `plugin:initError` — it only logs. This is an inconsistency relative to the boot-time `init(id)` path; see §"Open invariants."

The 2.58.0 `plugin.enabled` capability overlay is a **separate, parallel concept** sharing the word "enabled":

- Per-plugin `enabled` (this axis): is plugin X running at all? Persisted in `pluginState`.
- Capability `plugin.enabled` (the 2.58.0 overlay): is the 5-tool plugin-dev cohort admitted onto the active profile's tool surface? Persisted in `settings.plugin.enabled`. Resolved by [`resolvePluginConfig`](../js/profiles/resolve.js) + applied by [`applyPluginToolFilter`](../js/llm/api.js).

They are independent: a user can have every plugin disabled but the `plugin.enabled` overlay on (no plugins running, but the LLM can still drive the plugin editor via `read_plugin_source` etc.); a user can have every plugin enabled but the overlay off (plugins running, but the LLM has no plugin-dev tools available). The two come together at the `plugin-dev.v1` synthetic profile — switching to that profile gives both (every plugin runs + LLM has plugin-dev tools), without touching the overlay.

### Invocation axis — three surfaces + three side channels

The three primary surfaces:

1. **Hooks.** `Plugins.runHook(hookName, data) → Promise<data'>` ([`core.js:1144`](../js/core.js)) iterates `_hooks[hookName] || []` in registration order, awaiting each plugin's `manifest[hookName](data, instance, config)`. The return value chains: `data' = await hookFn(data, ...)`. **Hook function signature is `(data, instance, config)`** — three positional args; `instance` is the return of `init(config)`, `config` is the live `_registered[id].config` (mutated by `setConfig` mid-session). Per-hook errors are caught + logged ([`core.js:1156`](../js/core.js)); the chain continues with the un-transformed `data` for the failed plugin.
2. **Tools.** `Plugins.registerTool(pluginId, {name, description, parameters, roles, handler})` ([`core.js:1270`](../js/core.js)) lazily imports `ToolRegistry` (avoids the circular core↔registry dep), calls `ToolRegistry.register(name, handler, {type: 'function', function: {name, description, parameters}, roles: roles || 'all'})`, records `_toolOrigins.set(name, pluginId)` for the Settings UI attribution + the `tools:unregistered` cleanup listener. **The `roles` parameter passed through to `ToolRegistry.register` is dead-letter post-2.54.0** — admission is profile-side via `tools.admit`. The argument is preserved for back-compat with plugins that still pass it; the value lands in the registered definition's `def.roles` field where it's silently ignored by `Profiles.filterTools`. See §"Open invariants" for the gitea#443-tracked authoring-API question (how do user-authored plugins admit their tools onto picker profiles without `'*'` bypass?).
3. **UI buttons + modals.** `registerButton({icon, label, onClick})` ([`core.js:1237`](../js/core.js)) appends to `_buttons`; `getButtons()` ([`core.js:1242`](../js/core.js)) filters by per-plugin enabled state — disabled plugins' buttons hide. `registerModal({id, title, render, width})` ([`core.js:1249`](../js/core.js)) keys by `id` in `_modals`; `openPluginModal(id)` ([`plugin-modal.js:14`](../js/plugin-modal.js)) looks up + renders into `#pluginModalBody`. The modal's `render(body)` can return a string (set as `innerHTML`) or mutate the DOM directly + return undefined.

Three side channels:

1. **CSS injection.** `injectCSS(pluginId, cssText)` ([`core.js:1390`](../js/core.js)) writes a `<style id="plugin-css-${pluginId}">` element under `<head>`; `removeCSS(pluginId)` removes it. Multiple calls with the same `pluginId` replace the previous sheet (not append). CSS is global-scope — no shadow DOM, no scoping; plugins are expected to namespace their selectors.
2. **MCP server bring-your-own.** `registerMCPServer(pluginId, opts)` ([`core.js:1350`](../js/core.js)) wraps the MCP bridge `connect` cycle so a plugin can declare its own MCP server inline. The bundled `mcp-bridge` plugin uses this for the curated catalog entries. See [`ICD-mcp-bridge.md`](ICD-mcp-bridge.md) for the bridge contract this delegates to.
3. **Tool-origin attribution.** `_toolOrigins: Map<toolName, pluginId>` is populated by `registerTool`, drained by the `tools:unregistered` listener ([`core.js:1427`](../js/core.js)) when `ToolRegistry.unregister(name)` fires. `getRegisteredTools()` joins this map against the live registry to surface plugin-contributed tools in Settings → Plugins → "Plugin Tools" section. The 2.55.0 boot-warn site at [`tools/registry.js:100`](../js/tools/registry.js) reads this map to suggest which plugin a name belongs to.

### Cleanup axis — disable vs. uninstall vs. reload

Three teardown levels with strictly increasing thoroughness:

1. **Disable (`setEnabled(id, false)`).** Flag flips to false + persists + `plugin:enabledChanged` emits. Hooks stop firing (fan-out skips disabled plugins). Buttons hide (`getButtons()` filters). Tools **stay registered** — they're in `ToolRegistry`, not in `Plugins._registered`. CSS stays injected. Modals stay registered. The plugin's `instance` (init return value) stays alive — `runHook` reads it on every call; if the user re-enables, the same instance is reused (init skipped on re-enable, see Enablement axis invariant #2). **Reversible without reload.**
2. **Uninstall (`uninstallPlugin(url)` for externals; `_doDelete(tab)` for user plugins).** Source record is removed from `installedPlugins` / `userPlugins`. `setEnabled(id, false)` runs as part of the cascade. The runtime registration **survives** until reload — same property as Disable. UI hides the plugin from the Settings tab (since `installedPlugins` / `userPlugins` no longer lists it), but `Plugins.list()` still includes it (it's still in `_registered`). **Reversible up to reload boundary** — the user can technically re-install + the in-memory registration persists across reload via `pluginState` even though the source is gone (but `loadInstalledPlugins` won't re-fetch it because the URL record is gone, and `loadUserPlugins` won't re-import it because the source record is gone).
3. **Reload.** The blob-URL `import()` cache is flushed; the page restarts; only plugins with surviving persistence records re-load. **Fully reversible only at this level.**

The asymmetry — disable + uninstall both half-tear-down — is intentional and load-bearing. The reload escape hatch is the only fully reliable teardown path because the inline-eval model has no `unimport()` primitive + no way to track all side effects a plugin has accumulated (event listeners, intervals, mutated DOM, captured closures). Finding #1 (the unused `destroy()` hook) is the *partial* recovery — it would let cooperating plugins clean up their declared side effects on disable/uninstall, narrowing the reload gap.

## Open invariants

The ICD does not yet pin these. They are queued for a follow-up tightening session, gated on either a code session that touches the relevant call site or an architecture decision.

1. **Plugin-registered tool admission post-2.54.0.** `Plugins.registerTool(pluginId, {name, ..., roles, handler})` passes a `roles` arg through to `ToolRegistry.register`, which since the 2.54.0 admission inversion is **dead-letter**. The 2.55.0 boot-warn fires for plugin-registered tools that no profile admits — which is **every** plugin-registered tool name that doesn't match `'*'` / `'mcp__*'` / `'<some-prefix>__*'`, since picker profiles enumerate explicit names in `tools.admit` and plugin tool names are dynamic at register time. **Practical state today**: no bundled plugin under [`js/plugins/`](../js/plugins/) calls `Plugins.registerTool` (verified by grep at ICD-author time), so the warn doesn't fire in the default install. User-authored plugins **can** call it — those tools are reachable only via `full.v1`'s `'*'` sentinel bypass, not via picker profiles. The Phase 4 user-authoring API placeholder (gitea#443) is the tracked architectural ticket for this gap; admit-API design happens there. Until then: plugin authors who register tools should expect the boot-warn + admit through `full.v1` only.

2. **Hot-reload teardown semantics.** The plugin editor's Run button + `run_plugin` tool both call `Plugins.init(id)` after re-importing the source — but the existing `instance` is **not** torn down before re-init. A plugin whose `init` returns `{intervals: [setInterval(...)]}` will leak the prior intervals on every Run. The pattern works today because most plugins don't accumulate teardown-requiring state, but the ICD doesn't pin the contract: should re-register call `destroy(oldInstance, config)` before `init`? Same root question as finding #1; the answer should be unified.

3. **`init` error envelope inconsistency.** Boot-time `Plugins.init(id)` ([`core.js:1107`](../js/core.js)) catches init errors + emits `plugin:initError` for the Debug slide-out to surface. `setEnabled` first-enable init ([`core.js:1227`](../js/core.js)) catches + logs but **does not emit `plugin:initError`** — Settings-tab-toggled inits silently fail with only a console.error. Should the two error paths be unified? Or is the user-driven case "already in front of the UI, console suffices" different enough to keep distinct?

4. **`configSchema` field-type coverage.** The Settings UI's config-fields renderer ([`plugins-tab.js:193`](../js/settings/plugins-tab.js)) handles `text` / `password` / `textarea` types. The `select` / `number` / `boolean` types referenced in [`PLUGIN.md`](PLUGIN.md) (if present) would silently fall through to `text` input. The ICD doesn't enumerate the supported type set — would require reading the docs vs. code to settle.

5. **`Plugins.list()` order stability.** Returns `Object.values(this._registered).map(...)` ([`core.js:1178`](../js/core.js)) — JS object property iteration order is insertion-order for string keys, so the result is registration-order. The Settings UI relies on this for the All Plugins section render. Should it be pinned as a contract? Or is insertion-order stable enough that pinning is over-specification?

6. ~~**Auto-profile-switch interaction with per-chat profile binding.**~~ ✅ resolved at 2.66.0 — the auto-switch was retired entirely (finding #2 resolution C). The interaction question is moot: the 2.58.0 `plugin.enabled` capability overlay is now the sole admission path for the plugin-dev cohort, leaves both the global profile setting and per-chat binding untouched, and surfaces in-tab via the overlay banner at the top of the plugin editor. See finding #2 below for the retirement rationale.

## Code-aware findings

These three items surfaced during ICD authoring. Each was a candidate for a `[strong]`/`[medium]`-band roadmap row in the next code minor (2.64.0+). Finding #1 ✅ resolved at 2.64.0 (single-file fix in `Plugins.setEnabled` mirroring the first-enable init antibody one-for-one). Finding #2 ✅ resolved at 2.66.0 (resolution C — retire auto-switch; rely on the 2.58.0 `plugin.enabled` capability overlay with an in-tab opt-in banner). ### ~~Finding #1 [strong] — `destroy()` hook is declared in the contract but never invoked~~ ✅ resolved at 2.64.0

The plugin template at [`plugin-editor.js:51–93`](../js/plugin-editor.js) includes `async destroy(instance, config)` as a documented manifest hook; [`docs/PLUGIN.md`](PLUGIN.md) describes it as the cleanup contract for plugin disable + uninstall. The `Plugins` namespace **stores the manifest** including any `destroy` function, but **never calls it**. `setEnabled(id, false)` ([`core.js:1215`](../js/core.js)) flips the flag and persists state — no `manifest.destroy?.(plugin.instance, plugin.config)` invocation. `uninstallPlugin(url)` ([`plugin-loader.js:157`](../js/plugin-loader.js)) calls `setEnabled(false)` but doesn't separately invoke destroy. The reload-to-fully-remove property (Cleanup axis) is the safe-by-default fallback, but plugins that declare `destroy` for resource cleanup (timer cancellation, event listener removal, WebSocket close) will leak.

**Resolution at 2.64.0**: added the strict symmetric mirror of the first-enable init antibody at [`js/core.js:1227-1234`](../js/core.js). First-time disable (`!enabled && wasEnabled`) runs `manifest.destroy?.(instance, config)` when an instance was actually captured, catches + logs errors so a faulty cleanup hook never blocks the disable flag persistence, and clears the captured instance so a redundant second disable no-ops and a later re-enable runs init fresh. Four-part guard (`!enabled && wasEnabled && plugin.instance && plugin.manifest.destroy`) makes idempotency load-bearing. `uninstallPlugin` covered transitively through the existing `setEnabled(false)` cascade at [`plugin-loader.js:167-169`](../js/plugin-loader.js) (verified: only call site). Consciously changes Enablement-axis invariant #2 for the subset of plugins with destroy declared (re-init on toggle off→on is now correct because destroy released prior state); plugins without destroy preserve the prior no-re-init behavior. 4 new subtests in [`tests/test-plugin-lifecycle.mjs`](../tests/test-plugin-lifecycle.mjs) pin destroy invocation with `(instance, config)` + instance cleared + idempotency across two disables + throw-logged-but-disable-persisted + no-destroy-declared no-op.

**Band**: `[strong]`. Clear single-file fix, contract-documented hook that doesn't run, mechanical.

### ~~Finding #2 [medium] — auto-profile-switch on plugin-editor tab activation~~ ✅ resolved at 2.66.0

> **Resolved 2.66.0** — resolution **C** (retire). The `tab:switched` profile-mutation listener at the prior `plugin-editor.js:466–487` was deleted entirely; `_savedProfile` module state + `_syncProfileUI` helper removed alongside. The 2.58.0 `plugin.enabled` capability overlay is now the sole non-destructive admission path for the 5-tool plugin-dev cohort; an in-tab banner inside the plugin-editor tab body offers a one-click opt-in when the overlay is OFF (`#pluginEditorOverlayBanner` + `#pluginEditorOverlayEnable`) — `_readPluginOverlayEnabled` reuses `resolvePluginConfig` from [`js/profiles/resolve.js`](../js/profiles/resolve.js); `_enablePluginOverlay` mirrors the `_persistPlugin` shape from [`js/settings/tools-tab.js`](../js/settings/tools-tab.js) (no new persistence keys, no new event channels). All three failure modes (per-chat binding divergence, capability-overlay redundancy, restore-target staleness) eliminated. Synthetic `plugin-dev.v1` profile preserved for legacy `settings.role === 'plugin-dev'` migration + manual picker selection. Anti-regression pin at [`tests/test-plugin-editor-auto-switch-retired.mjs`](../tests/test-plugin-editor-auto-switch-retired.mjs) (4 subtests — source-scan idiom matching [`tests/test-chat-tool-name-literals.mjs`](../tests/test-chat-tool-name-literals.mjs)).

The pre-2.66.0 mechanism: [`plugin-editor.js:466–487`](../js/plugin-editor.js) subscribed to `tab:switched`; when the active tab is a plugin-editor tab, it swapped `State.settings.profile` to `'plugin-dev.v1'` (saving the previous value); when switching away, it restored. Persisted to `Storage` + emitted `profile:changed` with `auto: true`. The behavior predated per-chat profile binding (2.8.0) and the 2.58.0 `plugin.enabled` capability overlay.

Three failure modes the ICD authoring surfaced:

- **Per-chat binding divergence.** If the user is mid-conversation with profile `coder.v1`, opens the plugin editor, the global setting flips to `plugin-dev.v1`. The active chat's per-conversation profile binding is untouched — the LLM sees its bound profile, but the Settings UI shows `plugin-dev.v1`. The two diverge. The auto-switch was a 2.0.0 slice-3 update; per-chat binding came in 2.8.0; the interaction wasn't re-litigated.
- **Capability-overlay redundancy.** Post-2.58.0, the user can stay on their active profile + flip the `plugin.enabled` capability overlay ON to admit the 5 plugin-dev tools. The auto-switch is now a *third* admission path alongside picker-switch + overlay; it's the only one that mutates the global profile setting.
- **Restore-target staleness.** `_savedProfile` is captured on tab-enter; if the user changes the profile in another tab in the meantime (via Settings, or via a different chat's binding), tab-leave restores the **stale** value, silently undoing the user's mid-session profile change.

**Decision settled (2.66.0).** Resolution **C** chosen — retire the auto-switch entirely. The 2026-05-15 paper at [`docs/discussion/plugin-dev-mode-vs-profile.md`](discussion/plugin-dev-mode-vs-profile.md) had already settled plugin-dev as a *capability anyone can engage as needed*, not a *role someone takes on for a session*; the auto-switch was the last vestige of the pre-decision "burn working state on tab activation" shape. Resolutions A (keep+banner) and B (Settings-gate) were rejected: A preserves the three failure modes; B preserves two of three while adding a settings knob without resolving the overlay redundancy.

**Band**: was `[medium]`. Resolved at 2.66.0.

### ~~Finding #3 [strong] — invisible-Unicode scan findings not persisted to `InstalledPlugin` record~~ ✅ resolved at 2.65.0

> **Resolved 2.65.0** — opt-in `invisibleUnicodeFindings?: Array<{codepoint, name, line, col}>` added to the `InstalledPlugin` record; persisted on the bypass-install path via `_buildInstalledRecord`; Settings → Plugins external-row gains a `⚠ N flagged at install` badge with per-finding tooltip. Persistence-completeness contract pinned at [`tests/test-plugin-loader-invisible-unicode-persist.mjs`](../tests/test-plugin-loader-invisible-unicode-persist.mjs) (5 subtests). The bypass-and-install succeeds; the record at [`plugin-loader.js:129–135`](../js/plugin-loader.js) carries `error: null`. **The findings that triggered the prompt are not persisted to the `InstalledPlugin` record.**

Mirrors the 2.50.0 capabilities-shape persistence-completeness idiom (declare-then-pin shape).

**Band**: `[strong]`. Clear two-file fix (loader + tab UI), audit visibility is the goal, mechanical.

## Other observations

**No sandbox is by design.** Plugins run with full `window` + `AIEditor` access (per [`PLUGIN.md`](PLUGIN.md)). The pre-execution gates are: (a) invisible-Unicode scan, (b) AIEditor signature check, (c) user explicit confirmation on the install URL. The post-execution surfaces are: (d) per-plugin enabled state (toggleable in Settings), (e) the 2.58.0 `plugin.enabled` capability overlay gating the 5 plugin-dev tools, (f) reload-to-fully-remove. This is a different trust model than the Tier-0 LLM-authored automation Worker sandbox ([`DESIGN-llm-authored-automation.md`](DESIGN-llm-authored-automation.md)) — plugins are trusted-by-install (user explicitly added the source), Tier-0 scripts are untrusted-by-default (LLM emitted them, user reviews via approval card). The two share no code path.

**Three load paths, one in-process registry.** Bundled plugins (static imports in [`app.js`](../js/app.js)) + external plugins (URL → blob-import via [`plugin-loader.js`](../js/plugin-loader.js)) + user plugins (in-editor source → blob-import via [`plugin-editor.js`](../js/plugin-editor.js)) all flow into the same `Plugins.register(manifest)` entry point and share the same `_registered` / `_hooks` / `_buttons` / `_modals` state. The post-register lifecycle is uniform across the three sources; only the persistence record differs.

**Three EventBus events form the plugin lifecycle channel:** `plugin:registered` (after `register`), `plugin:enabledChanged` (after `setEnabled` flag flip), `plugin:initialized` (after `init` completes — boot-time or first-enable). The Debug slide-out's Plugins tab listens to all three for live status. Additional events: `plugin:installed` (after external install), `plugin:uninstalled` (after uninstall), `plugin:configChanged` (after `setConfig`), `plugin:buttonRegistered` / `plugin:modalRegistered` / `plugin:toolRegistered` / `plugin:mcpServerRegistered` / `plugin:initError` round out the surface.

**The 5-tool `PLUGIN_TOOL_NAMES` frozen array** ([`js/profiles/resolve.js`](../js/profiles/resolve.js)) is the single central membership list for the plugin-dev cohort: `read_plugin_source` + `write_plugin_source` + `run_plugin` + `list_user_plugins` + `read_docs`. Four of the five live in [`plugin-tools.js`](../js/tools/plugin-tools.js); `read_docs` is in [`doc-tools.js`](../js/tools/doc-tools.js) because reading `PLUGIN.md` + `TOOLS.md` is part of plugin authoring + not specific to the editor tab. The array is consumed in three places: (1) `applyPluginToolFilter` at [`js/llm/api.js`](../js/llm/api.js) — runtime filter when `plugin.enabled` overlay is OFF; (2) `findAdmittingProfiles(name, {overlayNames: PLUGIN_TOOL_NAMES})` at [`js/tools/registry.js`](../js/tools/registry.js) — boot-warn membership check; (3) the synthetic `plugin-dev.v1` profile's `tools.admit` list enumerates the same 5 names explicitly for the legacy switch path. Three consumers, one source of truth.
