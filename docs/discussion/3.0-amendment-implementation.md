# 3.0 — Amendment-implementation paper (substrate-change open questions)

> **Status:** Pre-architecture. Not a commitment. See [`README.md`](README.md).
> **Context:** The methodology amendment ([`methodology-amendment.md`](methodology-amendment.md)) describes the multi-role embodiment of the project's adopted methodology. This doc captures the **load-bearing open questions** a 3.0 architecture session would need to answer before 3.X.X work begins. It is *not* a design — it is the question list the design session inherits.
> **Trigger to promote:** Claude Design Touch 4 returns with UX direction on multi-role surfaces (see [`../design/touch-4-amendment-prompt.md`](../design/touch-4-amendment-prompt.md)). Sections that firm up become a `docs/DESIGN-amendment-runtime.md` design doc + a 3.X ROADMAP arc; sections that remain open stay here.
> **Hard prerequisite:** 2.X closes cleanly. The three 2.X tickets ([gitea#504](https://git.gobha.me/xcaliber/ai-editor/issues/504) introspection Phase 1, [gitea#505](https://git.gobha.me/xcaliber/ai-editor/issues/505) sub-agent model override, [gitea#506](https://git.gobha.me/xcaliber/ai-editor/issues/506) introspection Phase 2) pay forward into 3.X but do not assume the amendment shape — ship them under the current substrate.

## What's already decided (don't re-litigate)

Per the existing project record, these are not 3.0 questions:

- **Base methodology is in force.** Banded commitment gradient, document hierarchy, ICD discipline, re-evaluation cadence — all unchanged. The amendment is *additive*; nothing in the base goes away. (See [`../METHODOLOGY-coherence-at-speed.md`](../METHODOLOGY-coherence-at-speed.md) §21 of the amendment.)
- **No build step, no package.json, no framework, single-global-state.** Load-bearing per `project_constraints` memory. Any 3.X substrate must fit inside this envelope or earn an explicit, paper-grade carve-out — not drift past it.
- **Profiles are the role catalogs.** The 2026-05-15 profile-admission paper ([profiles-pick-tools.md](profiles-pick-tools.md), [plugin-dev-mode-vs-profile.md](plugin-dev-mode-vs-profile.md)) settled inversion + admission code + Roles→Profiles rename. Under 3.X, the amendment's roles (Architect, PM, Coder, Reviewer, Tester) map onto profile shapes — they do not reintroduce roles-as-tags.
- **Sub-agents are the fresh-per-event prototype.** `delegate_task` (2.49.0) + `subagent.v1` (read-only-by-default) + the approval card flow demonstrate the Coder-spawn pattern at small scale. The 3.X Coder is structurally the same shape, generalized.
- **The cheap-model lever is a hard prerequisite.** [gitea#505](https://git.gobha.me/xcaliber/ai-editor/issues/505) (per-profile / per-call model override) ships in 2.X. PM ticks running on Opus are economically infeasible; this lands before any 3.X work that depends on it.
- **Touch 3's Window v2 / Sessions composes here, not separately.** Per [touch-3-window-v2-sessions.md](touch-3-window-v2-sessions.md), Sessions was already parked post-2.0 and frames a session as "one profile, one tab, one branch, one chat." Under 3.X this generalizes: a session is also one queue scope, with the multi-role machinery operating within it. The Sessions architecture session and the 3.0 amendment-implementation session should run together — they are not separable.

## The load-bearing open questions

These are what the 3.0 architecture session has to settle. Each is a candidate for its own discussion doc once it surfaces.

### 1. The substrate inversion

Today, the conversation **is** the substrate. Plan slot, scratchpad, todo, sub-agent transcripts are adjuncts hanging off it. Under the amendment, the **work queue** is the substrate; the conversation is one view onto it.

Open:
- **Does ai-editor's chat history become the queue's event log, or does it stay as conversation-shaped and the queue lives separately?** First feels cleaner but breaks the existing `js/chat/history-store.js` contract every consumer reads from. Second preserves the chat surface but duplicates state.
- **Migration path for in-flight 2.X conversations.** Either (a) one-time migration at the 3.0 boundary, (b) coexistence — old conversations stay conversation-shaped, new sessions are queue-shaped, or (c) hard cut: 3.0 is a new product, old conversations are read-only archives.
- **The amendment says "queue is the single source of truth; roles read through operations, don't narrate from memory."** What does this look like for a fresh Coder spawn that's reading a queue item out of IDB? Does the input pack come from the queue itself or from a sibling curated store?

### 2. Statefulness for Architect and PM

Architect and PM are **stateful** — they wake on triggers, read their stored state + the queue, do work, write back. ai-editor today has no persistent stateful agent.

Open:
- **Where does role state live?** Appendix A proposes per-role markdown documents on disk. In a browser app with no filesystem, the analog is IDB + optional sync to `.aieditor/`. The `.aieditor/memory/*.md` convention (established at 1.3.0) is the precedent — extend it (`.aieditor/architect/state.md`, `.aieditor/pm/state.md`) or invert (`State.architect`, `State.pm` in IDB only)?
- **The scheduler.** PM wakes on scheduler tick + infrastructure event. Today's `setInterval` would work for ticks but is invisible to the user. Web Worker is the obvious alternative — does PM run in a Worker, or on the main thread?
- **Hibernation.** Sessions can sit idle for days. Stateful roles waking after long gaps need to re-read canonical sources without drift. The amendment names this (§19 "Stateful role drift" mitigation: re-read at each wake). What's the cheapest implementation that enforces it?

### 3. The dispatcher

Today the **user** is the dispatcher: they approve plans, accept memory proposals, hit approve on sub-agent cards. Under the amendment, PM dispatches mechanically and the user only sees escalations.

Open:
- **What does the user observe?** The amendment cuts the user out of the mechanical loop on purpose. But ai-editor users have grown used to controlling the cadence. UX question for Touch 4: how does a 3.X user perceive what the system is doing without being asked to approve every step?
- **Pause/resume granularity.** Amendment §15 names this — "current unit finishes, halt before next." But the *meaning* of "current unit" depends on which role's mid-task you are when pause hits. Surface design needs to make this legible.
- **Dispatcher cost ceiling.** Continuous PM ticks + occasional spawns can run away. The existing session cap in `subagent-tools.js:107` is the precedent — extend it to a full-system cap with per-role breakdowns, or treat PM ticks separately?

### 4. Profile shape under 3.X

Under the current substrate, profiles are "what kind of conversation do you want" (chat / coder / kb). Under the amendment, profiles are **role catalogs** — Architect-tools, PM-tools, Coder-tools, Reviewer-tools, Tester-tools. They are not user-picker entries; they are wired into the role bootstrap.

Open:
- **The picker collapses.** Today's `chat.v1` / `coder.v1` / `kb.v1` was a user-facing taxonomy. Under 3.X the user doesn't pick a role; the role runs based on event + queue. Does the picker still exist for human-driven chat (Q&A, doc work) as a fourth surface alongside the multi-role machinery, or does that surface fold into `kb.v1`-style work-as-a-Coder-task?
- **Legacy profiles (`chat.v1`, `plugin-dev.v1`, `pm.v1`, `reviewer.v1`, `full.v1`).** The 2.X picker had them all in [`js/profiles/registry.js`](../../js/profiles/registry.js). Under 3.X the meaningful subset is the role profiles. Strategy: rename + repurpose (e.g., `pm.v1` becomes the PM role's catalog), graceful-deprecate the rest, or hard-cut all and rebuild fresh?
- **The 3.X versioning shape.** Touch 4 / the 3.0 paper may settle on a per-role `*.v3` family (`architect.v3`, `pm.v3`, `coder.v3`, `reviewer.v3`, `tester.v3`) — explicit major-version step lets new and old coexist during migration.

### 5. The conversation as a view, not the system

Even with the queue as substrate, the **chat surface** is what the user spends time in. It cannot just disappear.

Open:
- **What does a Coder spawn look like in the chat surface?** A new "tab" inside a session, a sub-thread, a card-as-affordance? The amendment is structurally agnostic; Touch 4 must rule.
- **Where does the Architect's voice show up?** Architect is stateful and judgment-heavy. Touch 4 question: a dedicated Architect pane, an inline ticker, or "Architect speaks only on escalation"?
- **Escalation visibility.** When Reviewer escalates to PM to Architect to Human, the user is at the end of the chain. UX question: how does the user see the chain (who escalated what, when, why) without being overwhelmed?
- **Composition with Touch 3 Sessions.** A Session is "one profile, one branch, one chat" today. Under 3.X a Session contains a *queue* — the chat is its surface. Does a Session also contain its own PM tick, or is there one PM serving all Sessions in a window?

### 6. Cost model under multi-role

The amendment runs more agents simultaneously. Per `project_cost_quality_tradeoff` memory, minimizing spend without sacrificing context is the steering frame.

Open:
- **Per-role model defaults.** [gitea#505](https://git.gobha.me/xcaliber/ai-editor/issues/505) lands the lever; 3.0 settles which role gets which tier. First cut: PM ticks on the cheapest available model (read-mostly mechanical); Reviewer on a mid-tier (judgment but bounded); Coder default to the user's primary model; Architect on the primary model + occasional thinking mode; Tester on the cheap tier.
- **Cost cap composition.** Today's session cap is a single dollar cap. Under 3.X the user wants to see "PM ran X this week, Coder ran Y, escalations cost Z." The cost dashboard (`project_cost_dashboard_shipped`) is the precedent — extend it.
- **What's the worst-case cost per merged PR?** The amendment's tightest path: PM plans, Coder implements, Reviewer reviews, merge. Loosest: bounce loops, expected-breakage sub-task decomposition, precedent ratification. Need a budget envelope per merge before Touch 4 to constrain UX choices.

### 7. The introspection surface (load-bearing under 3.X)

The 2.X introspection tickets ([gitea#504](https://git.gobha.me/xcaliber/ai-editor/issues/504), [gitea#506](https://git.gobha.me/xcaliber/ai-editor/issues/506)) are how a fresh Coder reads what PM curated. Under 3.X they are not optional.

Open:
- **What does Coder read on spawn?** The amendment §7 lists what goes in the input pack. The introspection tools are how the Coder fetches it. Question: does the Coder *read* the pack at boot, or is it pre-loaded by PM into the spawn context?
- **Pack budgeting.** Amendment §7.2 names pack-budget silent truncation as a failure mode. Implementation: budget enforced at pack-build time, or at first-read time?

### 8. The precedent guard as concrete machinery

Amendment §14 — similarity query, ≥2 in 4 milestones → propose pattern ratification. Cheap to describe, real machinery to build.

Open:
- **Embedding-based vs hash-based?** Appendix A names both; the project already has embeddings infra (retrieval), so embedding-based is structurally cheaper. Threshold tuning is the real cost.
- **Where does the precedent store live?** IDB sibling to the queue, or rolled into the queue as a derived view?

## What this paper does NOT settle

- The actual queue schema (that's the 3.0 design doc's job).
- Specific role prompts (Appendix A of the amendment names them as project artifacts; they get authored alongside the 3.0 implementation).
- Migration order (which role's machinery lands first — likely PM since Coder already exists as `delegate_task`; ratification deferred).
- Cost-cap defaults (need the worst-case envelope from question 6 first).
- The picker question (question 4) until Touch 4 returns with the UX direction.

1. **2.X closes** with the three filed tickets (gitea#504, #505, #506) under the current substrate. Don't retrofit the amendment shape onto 2.X.

5. **3.X ROADMAP arc opens** — banded milestones per the base methodology, sized for one Coder spawn each (under the 2.X substrate; the amendment's Coder-fresh-per-spawn shape lands later in the arc, not at 3.0.0).
